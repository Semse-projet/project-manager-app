# Verified Contract Execution, Consent and Escrow Gate

> SDD 2.0 draft and evidence gate. Implementation/CI/deploy/activation statuses are not interchangeable, and these proposed requirements do not authorize sending live contracts.

## 1. Problema y resultado
Security release blocker #827: the legacy SEMSE signing endpoint can accept a caller-supplied documentHash/pdfUrl and set signature timestamps without independent provider verification. This is not equivalent to cryptographically verified electronic signing and must not unlock escrow. **Outcome:** a contract becomes `VERIFIED_EXECUTED` only with validated signer consent, matching original document/version and verified signed artifacts.

## 2. Alcance
**Included (proposed):** distinguish historical manual attestation from verified e-signature; refuse self-asserted provider completion; recipient-to-contract identity binding; immutable versioned PDF; capture provider certificate, SHA-256 and tamper-evident evidence; exact business authorization; escrow governance blockade until verified execution.
**Excluded:** granting agents signing powers, retroactively declaring old manual records legally verified, automatic escrow release based on provider status, generic "OPS_ADMIN" impersonation.

## 3. Actores, permisos y límites
- **Signer (client/professional):** authenticated as their canonical contract party, explicit consent for the final immutable document version, step-up where risk/legal requirements demand it; may sign only as self.
- **Tenant admin:** may select verified provider and request issuance under governed workflow; cannot forge either signer's assent.
- **Operations admin:** may investigate/remediate with audited override policy, but an override never stands in for human signature evidence.
- **Prometeo:** may draft, recommend provider and monitor; never send, impersonate or mark execution complete without required approval.
- **Provider webhook:** external, untrusted evidence hint; must pass authenticity, replay and scope; authenticated polling and artifact checks still required.

## 4. Escenarios críticos
```gherkin
DADO un contrato sin certificado PDF firmado por ambas partes
CUANDO un actor con permiso contracts:sign publica un hash o URL arbitraria
ENTONCES SEMSE NO convierte esa declaración en una firma electrónica verificada
Y no publica contract.fully_executed elegible para escrow
```
```gherkin
DADO una notificación VERIFIED del proveedor que no corresponde al tenant, contrato, versión o firmantes
CUANDO el reconciliador intenta completar el contrato
ENTONCES se rechaza, audita y mantiene el bloqueo de pagos
```
- [ ] Duplicados y replays son idempotentes; reversión/cancelación no habilita pago.
- [ ] Email/ID del firmante, versión de contrato y firma están vinculados criptográficamente o por certificado/audit trail verificable y reglas de identidad.
- [ ] No se aceptan `pdfUrl` arbitrarios para evidencia; fetch controlado contra proveedor verificado.
- [ ] Auditoría falla cerrada ante error (sin `catch(...).undefined` para evento crítico).

## 5. Contrato de API y UI
Current `POST /v1/contracts/:contractId/sign` and `/request-signatures` require a security migration. Target use separate operations: `REQUEST_APPROVED`, `SIGNER_CONSENTED`, `PROVIDER_COMPLETED`, `EVIDENCE_VERIFIED`, `CONTRACT_EXECUTED`; endpoints/schema subject to a later approved design. Preserve existing read compatibility but label legacy attestations as such; do not silently change semantics. UI must distinguish merely requested, provider-reported completed and verified signed.

## 6. FSM, eventos y reconstrucción
`DRAFT → APPROVED_TO_SEND → SENT → PARTIALLY_SIGNED → PROVIDER_COMPLETED → EVIDENCE_VERIFIED → VERIFIED_EXECUTED` with side branches declined/cancelled/expired/quarantined.
The only downstream escrow-eligible transition is **EVIDENCE_VERIFIED → VERIFIED_EXECUTED**, after Policy and verified signer identities. Emit authoritative immutable audit and decision lineage, not best-effort background task only. Replay reconstructs exact status with provenance.

## 7. Datos y migración
Future additive metadata should include tenant, connection, provider, external request ID, documentHash/version, signer roles and consent, verifiedAt, evidence URI/hash, audit certificate hash and provenance. No destructive conversion of old `signedClientAt`/`signedProAt`. Backfill must never presume prior verification. Feature flag phased, migration spec required before code changes.

## 8. Observabilidad
Metric: `unverified_escrow_attempts` = blocked; mismatch and tamper alarms; signed artifact retrieval age, verification failures. Evidence refs encrypted/restricted with immutable retention. Canary with synthetic test actors and approvals, no client transactions.

## 9. Tests requeridos
- [ ] Forged hash/URL; cross-tenant/cross-connection; OPS_ADMIN impersonation; altered signed PDF.
- [ ] Unauthenticated or replayed webhook, missing signed PDF/certificate, partial signatures, revocation.
- [ ] Crash between evidence storage and event; payment/escrow only on verified final execution.
- [ ] Regression historical data migration/no silent completion; smoke checks under least privilege.

## 10. Mapa de implementación
Affected: ContractsController/Service/Repository, payments/escrow policy, Evidence/Audit/Decision Ledger. Planned only — no signed-artifact enforcement implemented by this documentation.

## 11. Evaluación legal
Require jurisdiction-specific analysis (including ESIGN/UETA as applicable), consent presentation, identity assurance and provider certificate semantics; legal counsel sign-off where necessary. An API 'completed' flag is not a legal conclusion.

## 12. Gates
- [ ] Review #827 and approved security design; [ ] tests / threat model; [ ] provider artifact + identities proven.
- [ ] Exact SHA green, risk controls, no legacy path bypass; [ ] independent security review; [ ] staged rollout/rollback.
- [ ] No escrow production enablement until provable EVIDENCE_VERIFIED transition.


## 13. Entrega de ingeniería: evidencia candidata (PR posterior a #836)

**Estado: REVIEW / NO AUTORIZA FIRMA / NO ACTIVA ESCROW.**
La capa `SignatureEvidenceCapture` procesa exclusivamente una respuesta obtenida por un conector `AuthenticatedCompletionSource` desde una fuente de proveedor autenticada. Vincula exactamente tenant, conexión, contrato, ID de sobre externo y SHA-256 de la versión **original** del contrato. Exige dos firmantes, roles y userIds canónicos, email concordante, prueba declarada de consentimiento anterior a la firma y versión constante. Rechaza estado parcial, cancelado, identidad cruzada, documento faltante o referencias públicas.

Las verificaciones iniciales de bytes y SHA-256 de PDF/certificado **NO** validan todavía firma criptográfica integrada, cadena de certificados, revocación, sello de tiempo ni autenticidad jurídica del firmante. El adaptador real debe realizar autenticación del proveedor; el módulo **no confía** en un webhook o request body. Los `putImmutable` crean referencias privadas y la bitácora `ContractSignatureEvidenceCandidate` registra solamente `PENDING_VERIFICATION`, nunca `VERIFIED_EXECUTED`. En SQL el estado pendiente es obligatorio. No se proporciona endpoint para escribir estado verificado ni se registra el servicio para distribución en producción.

**Trust boundary siguiente (bloqueante):** implementar consulta autenticada Documenso (release/API verificada), descarga autenticada de PDF final + certificado, comprobación criptográfica con verificador independiente/CA y reglas de firma aplicables, storage privado real y política de retención. La promoción a `VerifiedContractExecution` requiere revisión de Policy/Approval, comparación con estado vigente y certificado y commit transaccional de bitácora/evento, sin aceptar valores arbitrarios desde interfaz.

**Escrow:** los endpoints actuales `deposit()`, `depositByJob()` y `release()`, más worker/reconciliador, necesitan inventario de canales y un gate independiente en cada operación económica. Nunca debe leerse `signedClientAt && signedProAt` como un hecho verificable. **No fusionar un bloqueo total a producción sin ruta válida para migrar contratos existentes, shadow telemetry, revisión legal y un canary controlado.** Ninguna fila histórica puede ascender automáticamente. Cualquier flag de rollout debe tener semántica documentada de seguridad y no puede otorgar una exención silenciosa o indefinida.

### Casos de aceptación de esta subentrega
- [x] Candidate server-only: no puede declarar `VERIFIED_EXECUTED`, incluso con proveedor COMPLETED.
- [x] Hash SHA-256 calculado sobre bytes reales de PDF y certificado.
- [x] Rechazo explícito de tenant/connection/contract/provider/envelope/version incorrectos.
- [x] Exactamente dos identidades y consentimiento ordenado; nunca suplantación por admin.
- [x] Escritura restringida a sobre `SENT` y unicidad compuesta de evidencias.
- [ ] Certificado/PDF firmado verificado criptográficamente con origen real de Documenso.
- [ ] Almacenamiento persistente real y recuperación por una identidad con mínimo privilegio.
- [ ] Promotion FSM `VERIFIED_EXECUTED` e historial/eventos atómicos.
- [ ] Gating de funding y todos los releases; pruebas adversarias con provider real.
- [ ] CI/SDD strict verde, aprobación, deploy y canary con evidencia SHA exacto.

### Consulta de artefactos Documenso (read-only, sin activación)
La implementación `DocumensoArtifactDownloader` consulta con token API de servidor y origen HTTPS fijo el sobre `GET /api/v2/envelope/{id}`, exige estado COMPLETED y dos recipients SIGNED; tras `outbox.assertOwned` descarga la versión `signed` del PDF y los PDF separados de certificado y audit log desde rutas V2 `/envelope/{id}/certificate/download` y `/envelope/{id}/audit-log/download`. Restringe redirects, IDs de ruta y tamaño de respuesta. **No está registrada como proveedor activo; el test usa mock fetch.** Tampoco genera consentimiento SEMSE ni verifica criptográficamente el CMS/X.509 o cadena de confianza.

Referencia de diseño (consultado el 8 oct 2026): https://openapi.documenso.com/ y https://docs.documenso.com/docs/developers/examples/common-workflows; fijar y contrastar los endpoints contra la versión autoalojada antes de activar.

## 14. Capa transaccional de escrow (PR apilado sobre #837)

**Alcance de este PR:** modelo independiente `VerifiedContractExecution` (sin writer, sin backfill, sin estado predeterminado); columna `Contract.canonicalPdfSha256` **exclusivamente server-owned** para ligar la versión original; guard `assertVerifiedEscrowReservation()` llamado dentro de `PaymentsRepository.depositFunds` y `PaymentsRepository.releaseFunds` antes de reservar el movimiento, en la misma transacción de Prisma. Este punto de control cubre el depósito directo por proyecto, depósito por job y liberaciones manuales, desde agentes y automáticas que usan esos dos métodos de repositorio. El `FOR SHARE` bloquea actualizaciones revocadoras concurrentes mientras se hace la reserva.

**Modalidades temporales:** `SEMSE_VERIFIED_ESCROW_MODE=shadow` (valor predeterminado de esta propuesta) calcula bloqueos y observa sin impedir operaciones económicas, para estudiar datos históricos. `enforce` niega todas las operaciones sin `VerifiedContractExecution` válido, vinculando tenant, contrato, versión original, los dos usuarios, hashes PDF/certificado/log, decisión aprobada y timestamps de verificación; el fallo de DB o la falta de fila bloquea. Las operaciones históricas carecen de `canonicalPdfSha256` y no deben convertirse automáticamente. `off` es inválido. En consecuencia **el modo shadow no satisface #827 ni se considera activación segura**. El cambio a enforce requiere staging completo, tratamiento contractual/legal de operaciones preexistentes y aprobación explícita, no un simple merge.

**Condiciones de cierre que siguen sin resolverse:** producir PDF original canónico de servidor (no documentHash del cliente); implementar verificación CMS/PAdES y cadena/tiempo de certificados, validación independiente de consent/identidad y almacenamiento privado montado; workflow de promoción transaccional más audit/Decision Ledger; migraciones en staging, e2e con sobre real Documenso, casos con cobros existentes y canary. No registrar `VerifiedContractExecution` desde webhook, request body, `OPS_ADMIN` ni mero COMPLETED del proveedor. Un experto de seguridad debe revisar cada ruta adicional que no atraviese `PaymentsRepository`.

**Prueba de migración segura:** en staging, configurar `enforce`, esperar bloqueo para legacy y prueba positiva solo con prueba verificada generada por el flujo confiable; registrar trazabilidad antes/después, rollout shadow → canary → enforce con rollback explícito. El baseline de producción permanece intacto.
