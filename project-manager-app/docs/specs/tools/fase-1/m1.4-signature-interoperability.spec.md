# Provider-neutral electronic signatures — proposed extension of M1.4

This is a separate SDD 2.0 specification. The historical M1.4 spec remains unchanged and retains its historical status. These new signature-provider capabilities are **not** certified, merged, deployed, or activated.

## Proposed extension — Provider-agnostic signature interoperability (2026-10-08)

> **Status: PROPOSED / NOT IMPLEMENTED / NOT LIVE.** This section does not change the VERIFIED status of the historical M1.4 scope. It does not authorize production signature requests or migrations.

### Product intent

SEMSE owns the contract lifecycle, signer consent, policy decisions, immutable evidence references and audit trail. A self-hosted open-source signing provider (candidate: Documenso; license, API features, hosting and legal suitability must be verified) is the default *option*, not a promise of zero downtime. A tenant may instead connect an authorized external provider already used by its customer, subject to that provider's official API, plan, permissions and interoperability limitations. A client must never be told that an existing account is connected until an authenticated provider connection has actually been verified.

### Canonical design and integration boundaries

- Reuse `Dashboard → Settings → Integraciones` as the administrative control plane. Do not create a competing connector registry or expose provider credentials in the browser.
- Reuse `platform.universal-connector-trust` (ADR-042) for tenant/connection isolation, capabilities, least privilege, Policy/Approval, idempotency, webhook authenticity, replay defense, emergency stop and evidence lineage. The shared contract is **not** proof that a production adapter is already active.
- Introduce a provider-neutral signature port with `createRequest`, `getRequestStatus`, `cancelRequest` where supported, `verifyWebhook`, `fetchCompletedArtifact` and capability discovery. Providers declare unsupported capabilities explicitly; no fabricated interoperability.
- Candidate adapters: self-hosted Documenso, Dropbox Sign (existing), DocuSign, and later other providers after contract and security review. Existing Dropbox Sign integration remains available during migration; no destructive schema change.
- Contract record must retain tenantId, contractId, providerId, connectionId, externalRequestId, signer identities/roles, requested/verified timestamps, status provenance, consent and evidence references. Never store credentials, signing tokens or unredacted documents in logs.
- Tenant admin selects an approved connection, or SEMSE applies a documented tenant default. No automatic switch of provider after a request is created; fail explicitly and reconcile to prevent duplicate or legally ambiguous signature requests.
- Signing status must come from verified provider callbacks or authenticated polling, with idempotent transitions and a reconciler. Only verified fully executed documents may unblock downstream escrow conditions; an API connectivity check alone is insufficient.
- **Fail closed:** no silent mock fallback in production. Existing `HelloSignService` currently sends `test_mode=1` and returns mock results after provider errors; remove this behavior only in a separately reviewed implementation PR with regression tests, migration/rollout strategy and explicit activation gate.
- Document and verify retention, data residency, e-signature consent, audit certificate, signer authentication and applicable legal requirements per provider and jurisdiction; do not claim universal legal equivalence.

### Delivery slices and acceptance evidence

1. **Inventory and threat model:** trace all existing contract endpoints, UI, settings, provider calls, audit and webhook handlers; map live/mock paths and tenant boundaries. No changes to production credentials.
2. **Port and tests:** provider-neutral types, capability registry, deterministic fake adapter only for tests, and contract tests for tenant isolation, permissions, fail-closed errors, idempotency and no duplicate requests.
3. **Existing Dropbox Sign adapter:** remove implicit mock fallback and unconditional test mode behind explicit rollout controls; ensure existing contracts remain readable and no real requests are sent during tests.
4. **Open-source provider adapter:** select and license-review a concrete version; deploy isolated infrastructure with persistence, secrets, backups, health checks, callback validation and rollback. Test with non-production documents and consenting test signers.
5. **External adapters:** integrate providers individually using official supported APIs; verify OAuth/API-key scopes and customer authorization, then webhook/polling and evidence retrieval.
6. **UI and production gates:** reuse Integraciones for connection lifecycle and tests; add provider selection to contract workflow. Require typecheck, build, automated tests, security/secret scan, CI on exact SHA, successful Railway deploy, authenticated smoke tests, and operator-approved activation before declaring LIVE.

**Out of scope for this documentation-only change:** changing Railway variables, sending signatures, merging code, modifying payment/escrow policy, claiming providers connected, or activating live traffic.
