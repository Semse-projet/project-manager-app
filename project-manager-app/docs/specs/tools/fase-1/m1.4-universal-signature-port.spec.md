# Provider-Neutral Signature Port and Registry

> SDD 2.0 — retroactive governance specification for an *in-progress draft* implementation. This artifact is not a production certification, nor an approval to send/sign contracts.

## 1. Problema y resultado
SEMSE currently couples signature initiation and storage to Dropbox Sign. A provider-neutral port is needed to support self-hosted Documenso and customer-authorized external signing services without losing contract ownership. **Success:** callers can select only a registered, approved tenant connection and receive truthful status/receipts without conflating "sent" and "signed".

## 2. Alcance
**Included:** strongly typed signature request/receipt/signers, provider capabilities, `SignatureProviderRegistry`, tenant+connection scoping, idempotency-key contract, unknown-provider fail-closed behavior (PR #824, expanded by #825/#826).
**Excluded:** live connector registration, provider network implementation, full webhook/polling reconciler, escrow release, and credential authorization by the registry itself.

## 3. Actores, permisos y límites
- SEMSE canonical policy/approval owns permissions and business effects; providers implement transport only.
- Tenant/connection IDs come from **trusted** runtime state, not from caller-controlled payload; signing service verifies contract ownership.
- Human approval is required before distribution; Prometeo has proposal-only authority unless a separate explicit delegation exists (never to sign as human).
- Provider capability discovery describes feature support, not permission or verified operational readiness.

## 4. Escenarios de aceptación
```gherkin
DADO una petición autorizada vinculada a tenant y connectionId
CUANDO el motor resuelve un proveedor registrado
ENTONCES el puerto mantiene la misma semántica de solicitud, estado y evidencia
Y cualquier proveedor ausente o capacidad no soportada falla explícitamente
```
```gherkin
DADO un recibo de tipo SENT/PENDING
CUANDO SEMSE evalúa si un contrato está firmado
ENTONCES NO trata dicho recibo como documento ejecutado ni como evidencia de escrow
```
- [ ] Duplicate provider registration fails; unknown identifier fails.
- [ ] Tenant / connection mismatch and missing approval prevent provider invocation.
- [ ] Duplicate key with conflicting fingerprint never dispatches again.

## 5. Contratos
`SignatureProvider` target operations: `createRequest`, `getRequestStatus`, optional `cancelRequest`, `verifyWebhook`, `fetchCompletedArtifact`; provider manifest must declare supported operations explicitly. Current PR offers initial create/status only; unsupported capabilities cannot be implied. Keep `completedDocumentRef: null` until artifact retrieval and validation.

## 6. FSM y eventos
Shared semantic states: pending, partially_signed, completed, declined, cancelled. **Completed** is only a reported provider state, not proof of legally executed SEMSE contract without verified signed PDF, recipients, version and certificate. Event publishing/consumption requires durable idempotence and Policy.

## 7. Datos y migración
None in #824; later journal in #826. Never destructively rewrite HelloSign fields. Future adapter changes must maintain schema and historical read paths.

## 8. Observabilidad y rollout
Record provider ID, trusted connection ID, tenant, document/version hash and correlation reference (not signing tokens). Rollout: registry tests → approved outbox integration → test-only canary → provider status reconciliation → production readiness. Hard-disabled unless runtime explicitly allows execution.

## 9. Pruebas
- [x] Missing/duplicate provider unit cases authored in #824.
- [ ] Simulated cross-tenant and cross-connection callers, approval revocation, replay collision, unsupported capability.
- [ ] Conformance suite on every adapter, production CI exact SHA.
- [ ] Evidence cannot be inferred from request receipt.

## 10. Implementación
PR #824 defines the initial port; #825 adds Documenso adaptation; #826 adds connection scoping and durable outbox. Bind to existing ADR-042 Universal Connector runtime, **never** a second ad-hoc policy engine.

## 11. Investigación
Verify API-level feature parity individually for Documenso, Dropbox Sign, DocuSign; do not claim portability of signing sessions or completed envelopes.
