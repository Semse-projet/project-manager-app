# Dropbox Sign Fail-Closed Provider Hardening

> SDD 2.0 — retroactive governance specification for an *in-progress draft* implementation. This artifact is not a production certification, nor an approval to send/sign contracts.

## 1. Problema y resultado
- **Actors:** SEMSE clients, professionals, administrators and authorized provider runtime.
- **Problem:** the legacy HelloSign/Dropbox Sign client can fabricate a mock signature request on missing credentials or provider errors; `test_mode=1` is always sent, and requests can appear successful when they are not legally effective.
- **Outcome:** real-provider failures never become simulated success in production. Existing records remain readable; actual production sends require separate release approval.

## 2. Alcance
**Included:** strengthen `HelloSignService`, eliminate silent mock fallback on HTTP 4xx/5xx/malformed response/timeout, reject missing live configuration, preserve explicit test-only behavior, sanitize errors, and add negative tests (PR #823).
**Excluded:** enabling live sends, Documenso integration, signer impersonation fixes (tracked separately), and payment/escrow activation.

## 3. Actores, permisos y límites
| Actor | Authoritative capability | Resource scope | Permitted | Forbidden |
|---|---|---|---|---|
| Tenant admin | verified integration + `contracts:create` + Policy/Approval | own tenant/contract | request approval of sending | turn test receipt into signed contract |
| Client/professional | authenticated signing identity + explicit consent | their agreement | sign by provider flow | silently sign for another party |
| Prometeo | delegated propose/draft | tenant/purpose | prepare contract | send, sign or grant approval |
| Provider service | server secret reference | tenant/connection | execute already authorized command | decide SEMSE consent or escrow eligibility |

Credentials never reach browser, untrusted documents, Prometeo or logs. No cross-tenant access. A generic `contracts:create` permission is not, by itself, approval to dispatch.

## 4. Escenarios y aceptación
```gherkin
DADO una conexión Dropbox Sign con credencial configurada
CUANDO el proveedor responde HTTP 401, 429, 500, timeout o JSON incompleto
ENTONCES SEMSE retorna un fallo explícito sin `mock_sr_`
Y no registra estado "sent", "signed" ni desbloquea escrow
```
```gherkin
DADO NODE_ENV=production sin credencial de firma
CUANDO se intenta enviar un contrato
ENTONCES se rechaza la operación sin generar enlaces simulados
```
- [ ] La producción no activa firmas reales mientras `test_mode=1` continúe fijado.
- [ ] Casos de contrato histórico leídos sin mutaciones y sin pérdida de URLs anteriores.
- [ ] Retries tras error ambiguo pasan por idempotency/outbox, no reenvío ciego.

## 5. Contratos
Existing route `POST /v1/contracts/:contractId/request-signatures`: preserve response envelope compatibility only when the provider confirms a request; errors explicit and sanitized. Signer inputs must be checked against canonical parties in a later authorization gate. Never claim a successful provider API connection proves a signature.
UI: distinguish test, unconfigured, failed, sent, pending and verified-complete states; no fake CTA.

## 6. FSM y eventos
`DRAFT → APPROVED_TO_SEND → PROVIDER_PENDING → PROVIDER_COMPLETED → VERIFIED_SIGNED` is the target; this PR implements only safer provider error semantics. Events such as `contract.signature_requested` require a confirmed provider receipt; `contract.fully_executed` requires verified evidence and authorized actors. No direct activation of escrow by this PR.

## 7. Datos y migración
No schema change in PR #823. Existing `helloSignRequestId`/signing URLs remain readable; future provider-neutral records must migrate additively. Do not overwrite historical data. Rollback is code-level, with signing disabled before reverting fail-closed guarantees.

## 8. Observabilidad y activación
Metrics: rejected provider request, HTTP error class, missing credentials, unexpected mock in production (must equal zero). Logs contain correlation IDs, not provider bodies or secrets. Canary only with consenting test actors, exact SHA CI, permissions audit and explicit operations approval.

## 9. Pruebas
- [x] Regression tests authored for 401 and missing credentials in production (#823); passing CI does not imply real-service certification.
- [ ] Failures for malformed JSON/timeout/429/5xx and partial acknowledgment with no mock fallback.
- [ ] Authorized signer and recipient canonical mapping; replay/isolation; no escrow release.
- [ ] Production-config integration smoke without signing real client documents.

## 10. Mapa de implementación
PR #823 modifies the existing HelloSign adapter and service behavior. No runtime provider switch, Railway configuration, or signing activation belongs in this change.

## 11. Investigación y riesgos externos
Validate vendor API rate limits, test-mode behavior, authentication and signing evidence against the vendor's official documentation at version pinning. No presumed equivalence of test-mode and binding production signatures.
